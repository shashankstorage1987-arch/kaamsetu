API Endpoint: POST /api/v1/auth/signup/worker
-------------------------------------------------------------------------------
Source Reference: Tech Spec Section 7 (Auth) & Wireframe Screen 1.1
Auth Requirement: Unauthenticated (Public)
Allowed Role: Anyone
Request Payload:
{
  "full_name": "string (mandatory)",
  "phone_number": "string (mandatory, 10 digits)",
  "pin": "string (mandatory, 6 digits)",
  "aadhaar_number": "string (mandatory, 12 digits)"
}
Response Payload (201 Created):
{
  "user_id": "UUID",
  "phone_number": "string",
  "role": "WORKER",
  "token": "string (JWT token)"
}
Validation Rules: Phone 10 digits, PIN 6 numeric digits, Aadhaar 12 numeric digits, phone must be unique.
Database Entities Used: users (`aadhaar_verified`, `aadhaar_ref_id`)
Business Rules:
- The raw 12-digit Aadhaar number may be transmitted only as part of the secure verification request required by the Aadhaar verification service. It MUST NEVER be persisted in the KaamSetu database, written to application logs, returned in any API response, stored in browser/local/session storage, included in audit metadata, or otherwise retained after verification processing (BR-Aadhaar).
- System performs verification against integration provider, persisting `aadhaar_verified = TRUE` and verification reference token `aadhaar_ref_id` ONLY. Raw Aadhaar is discarded immediately after verification processing.
- External verification provider marked: `PENDING INTEGRATION DECISION`.
- PIN hashed via bcrypt/argon2 (BR-006); worker verification is Aadhaar ID-only for MVP (BR-003).
Error Conditions:
- 400 Bad Request (Validation failure)
- 409 Conflict (Phone number already registered)
Audit Logging Requirement: Write to audit_logs ("WORKER_REGISTERED")
Redis Dependency: None
External Integration: Aadhaar Verification Provider (Mock/Stub for MVP - marked `PENDING INTEGRATION DECISION`)

API Endpoint: POST /api/v1/auth/logout
-------------------------------------------------------------------------------
Source Reference: Tech Spec Section 7 (Auth) & Resolved Decision 9 (Multi-Device FCM)
Auth Requirement: Authenticated
Allowed Role: All roles
Request Payload:
{
  "fcm_token": "string (optional - current device token to deactivate)"
}
Response Payload (200 OK):
{
  "message": "Logged out successfully"
}
Validation Rules: Valid JWT token.
Database Entities Used: user_devices
Business Rules:
- Invalidates calling JWT token on server via Redis blocklist.
- Deactivates ONLY the current device's active FCM token in `user_devices` (`active = false`). Other active devices belonging to the user remain registered and active (BR-MultiDeviceLogout). FCM tokens are never treated as a single user-level token.
Error Conditions: 401 Unauthorized
Audit Logging Requirement: None
Redis Dependency: Redis blocklist `jwt_blocklist:{token}`.
External Integration: None

API Endpoint: GET /api/v1/search/workers
-------------------------------------------------------------------------------
Source Reference: Tech Spec Section 7 (Employer) & Wireframe Screen 4.1 / 4.3
Auth Requirement: Authenticated
Allowed Role: EMPLOYER
Query Parameters:
- trade (string, default: employer's business_trade)
- profession (string, optional)
- available_now (boolean, default: false)
- verified (boolean, default: false)
- salary_max (integer, optional)
- experience_min (numeric, optional)
- radius_km (numeric, default: 1.0, progressive values: 1.0, 3.0, 5.0, 10.0 max)
Response Payload (200 OK):
{
  "total_found": 6,
  "radius_km": 1.0,
  "workers": [
    {
      "worker_id": "UUID",
      "full_name": "Raj Kumar",
      "trade": "ELECTRICAL",
      "profession": "HELPER",
      "experience_years": 5.0,
      "distance_km": 0.8,
      "is_available": true,
      "aadhaar_verified": true,
      "match_score": 88.0
    }
  ]
}
Validation Rules: radius_km > 0 and <= 10.0.
Database Entities Used: worker_profiles, worker_experience, users
Business Rules:
- Search is the primary employer discovery mechanism (BR-001).
- Opens with employer's business trade as default filter.
- Widen Search advances radius along progression: 1km -> 3km -> 5km -> 10km max (BR-WidenSearch).
- Workers outside radius excluded entirely via PostGIS `ST_DWithin`.
- Response time target < 1 second.
Error Conditions: 400 Bad Request
Audit Logging Requirement: None
Redis Dependency: Caches hot search results `search:{hash}` for 30 seconds.
External Integration: PostGIS spatial engine

-------------------------------------------------------------------------------
API Endpoint: POST /api/v1/hire-confirmations/{id}/respond
-------------------------------------------------------------------------------
Source Reference: Tech Spec Section 7 (Hire), Wireframe Screen 9.1 / 9.2 & Phase 0.2 Lifecycle Specification
Auth Requirement: Authenticated
Allowed Role: WORKER
Request Payload:
{
  "confirmed": "boolean (mandatory)"
}
Response Payload (200 OK):
{
  "hire_confirmation_id": "UUID",
  "status": "CONFIRMED | MISMATCH",
  "confirmed_at": "ISO-8601 Timestamp"
}
Validation Rules: confirmed field boolean mandatory. Pending record must exist.
Database Entities Used: hire_confirmations, worker_profiles, audit_logs
Business Rules:
- If confirmed = true: sets `worker_confirmed = true`, `status = CONFIRMED`. Hire is fully confirmed. Dynamically increments worker's 3-month completed hires count.
- If confirmed = false: sets `worker_confirmed = false`, `status = MISMATCH`. The hire is NOT confirmed. THE JOB REMAINS `CLOSED` (does not automatically reopen). Employer must create a new job if they wish to search again. Auto-writes `HIRE_MISMATCH_FLAGGED` in `audit_logs` for admin review (BR-004).
Error Conditions: 400 Bad Request, 404 Not Found
Audit Logging Requirement: Write to audit_logs ("HIRE_CONFIRMED" or "HIRE_MISMATCH_FLAGGED")
Redis Dependency: None
External Integration: None

API Endpoint: POST /api/v1/users/me/fcm-token
-------------------------------------------------------------------------------
Source Reference: Tech Spec Section 8 (PWA) & Resolved Decision 9 (FCM Device Model)
Auth Requirement: Authenticated
Allowed Role: All authenticated roles
Request Payload:
{
  "fcm_token": "string (mandatory)",
  "platform": "WEB | ANDROID | IOS (optional, default: WEB)"
}
Response Payload (200 OK):
{
  "device_id": "UUID",
  "active": true,
  "registered_at": "ISO-8601 Timestamp"
}
Validation Rules: fcm_token non-empty.
Database Entities Used: user_devices
Business Rules:
- Persists device token into `user_devices` table.
- Supports multi-device registration per user. Prevents token duplication per user.
- FCM tokens are NEVER exposed in normal user API responses (BR-DeviceTokens).
- Deactivated on logout (`active = false` for calling device).
Error Conditions: 400 Bad Request, 401 Unauthorized
Audit Logging Requirement: None
Redis Dependency: None
External Integration: Firebase Cloud Messaging SDK
