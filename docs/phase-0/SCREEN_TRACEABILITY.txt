1. FLOW 01: LOGIN, SIGN UP & WORKER ONBOARDING
===============================================================================

-------------------------------------------------------------------------------
Screen: 1.0 Login (kaamsetu.app/login)
-------------------------------------------------------------------------------
User Flow: Flow 01 — Login & Sign Up
Backend API: POST /api/v1/auth/login
Database Entity: users
Business Rules:
- PIN, not OTP, is the everyday login mechanism (BR-006).
- Account locked temporarily after 5 failed attempts in 15 minutes.
External Integration: Redis (rate limiting)
Validation: Phone number 10 digits, PIN 6 numeric digits.
Test Requirement: Verify successful login with valid credentials, failed login with invalid PIN, rate limit lockout after 5 failed attempts.

-------------------------------------------------------------------------------
Screen: 1.0b Sign Up Choice (kaamsetu.app/signup)
-------------------------------------------------------------------------------
User Flow: Flow 01 — Login & Sign Up
Backend API: NOT DEFINED IN SOURCE (Client-side routing view)
Database Entity: None
Business Rules: User chooses role (WORKER or EMPLOYER) to determine onboarding path.
External Integration: None
Validation: Selection required.
Test Requirement: Verify navigation to Worker Sign Up (1.1) vs Employer Sign Up (3.1).

-------------------------------------------------------------------------------
Screen: 1.1 Worker Sign Up (kaamsetu.app/signup/worker)
-------------------------------------------------------------------------------
User Flow: Flow 01 — Worker Onboarding
Backend API: POST /api/v1/auth/signup/worker
Database Entity: users (`aadhaar_verified`, `aadhaar_ref_id`)
Business Rules:
- Worker verification is ID-only (Aadhaar reference) for MVP (BR-003).
- The raw 12-digit Aadhaar number may be transmitted only as part of the secure verification request required by the Aadhaar verification service. It MUST NEVER be persisted in the KaamSetu database, written to application logs, returned in any API response, stored in browser/local/session storage, included in audit metadata, or otherwise retained after verification processing (BR-Aadhaar). Only `aadhaar_verified = TRUE` and verification reference string (`aadhaar_ref_id`) are stored.
- Plaintext PIN must never be stored; hash using bcrypt/argon2.
External Integration: Aadhaar Verification Provider (Mock/Stub for MVP - marked `PENDING INTEGRATION DECISION`)
Validation: Full name non-empty, phone 10 digits, PIN 6 digits matching Re-enter, Aadhaar 12 digits.
Test Requirement: Verify account creation, password hashing, duplicate phone rejection, Aadhaar non-persistence.

-------------------------------------------------------------------------------
Screen: 1.2 Work Experience — Skill Passport 1/3 (kaamsetu.app/onboard/experience)
-------------------------------------------------------------------------------
User Flow: Flow 01 — Worker Onboarding & Profile Edit
Backend API: PATCH /api/v1/workers/me
Database Entity: worker_profiles, worker_experience
Business Rules:
- Core skills and experience are self-reported and unverified (BR-003).
- Multiple shop experiences supported per worker.
- Re-visited during Profile Edit mode from Worker Self-Profile (4.2).
External Integration: None
Validation: Total experience numeric, Trade & Profession selected from taxonomy, previous employer non-empty, languages selected.
Test Requirement: Verify saving experience array, trade taxonomy adherence, profile edit updates.

Database Entity: worker_experience, worker_profiles
Business Rules: Captures total experience, trade, profession, previous shop, languages (BR-003).
External Integration: None
Validation: Total experience numeric positive, primary trade required, profession required, at least 1 language.
Test Requirement: Verify experience entries saved, multiple experience rows created.

-------------------------------------------------------------------------------
Screen: 1.3 Worker Address — Skill Passport 2/3 (kaamsetu.app/onboard/address)
-------------------------------------------------------------------------------
User Flow: Flow 01 — Worker Onboarding & Profile Edit
Backend API: PATCH /api/v1/workers/me
Database Entity: worker_profiles.location
Business Rules: Address text geocoded to PostGIS geography Point(lon, lat).
External Integration: Google Maps Geocoding API
Validation: House/street, area/locality, city non-empty, pincode 6 digits.
Test Requirement: Verify geocoding integration, PostGIS Point conversion, geocoding failure handling.

-------------------------------------------------------------------------------
Screen: 1.4 Job Preferences — Skill Passport 3/3 (kaamsetu.app/onboard/preferences)
-------------------------------------------------------------------------------
User Flow: Flow 01 — Worker Onboarding & Profile Edit
Backend API: PATCH /api/v1/workers/me
Database Entity: worker_profiles
Business Rules: Setting Available Now toggle stores initial profile preference (`is_available` boolean) during onboarding in Phase 1. It does NOT invoke `PATCH /api/v1/workers/me/availability` or start the Phase 3 real-time availability auto-expiry engine (BR-002).
External Integration: None
Validation: Preferred salary numeric positive, preferred distance numeric positive.
Test Requirement: Verify saving preferences, initial availability toggle status.

4. FLOW 04: EMPLOYER SEARCH — PRIMARY ACTION
===============================================================================

-------------------------------------------------------------------------------
Screen: 4.1 Search & Filters (kaamsetu.app/search)
-------------------------------------------------------------------------------
User Flow: Flow 04 — Employer Search
Backend API: GET /api/v1/search/workers
Database Entity: worker_profiles, worker_experience, users
Business Rules:
- Search is the primary employer discovery mechanism (BR-001).
- Opens with employer's business trade as default filter.
- Workers outside radius are excluded entirely.
- Expired availability workers excluded when Available Now filter active.
External Integration: PostGIS (`ST_DWithin`, `ST_Distance`)
Validation: Search radius > 0.
Test Requirement: Verify dynamic multi-filter SQL queries, response time < 1s, distance filtering accuracy.

-------------------------------------------------------------------------------
Screen: 4.2 Skill Passport (kaamsetu.app/worker/{id})
-------------------------------------------------------------------------------
User Flow: Flow 04 — Employer Search & Worker Self-Profile
Backend API: GET /api/v1/workers/{id}, GET /api/v1/workers/{id}/contact (Employer view only)
Database Entity: worker_profiles, worker_experience, hire_confirmations, audit_logs
Business Rules:
- Dual perspective screen:
  * Employer View: Displays "View Contact Number" and "Report this worker". Contact number returned ONLY upon explicit GET /workers/{id}/contact call (creates audit log).
  * Worker Self-View: Omits Contact Reveal & Report links; displays prominent "Edit Profile" button routing to 1.2/1.3/1.4 (BR-WorkerProfile).
- "Shop categories worked in" derived dynamically from unique `trade` ENUMs in `worker_experience` (BR-ShopCategories).
- "Recently completed hires" calculated dynamically via `COUNT(hire_confirmations)` in 3-month window (BR-HiresCount).
External Integration: None
Validation: Authenticated session required.
Test Requirement: Verify employer view vs worker self-view rendering, masked phone number response, derived shop categories, dynamic hires count.

-------------------------------------------------------------------------------
Screen: 4.3 No Match — Zero State (kaamsetu.app/search)
-------------------------------------------------------------------------------
User Flow: Flow 04 — Employer Search
Backend API: GET /api/v1/search/workers (returns 0 results)
Database Entity: None
Business Rules:
- "Widen Search" advances radius along fixed progression: 1km -> 3km -> 5km -> 10km (capped at 10km) (BR-WidenSearch).
- Posting a job is framed strictly as a fallback when search returns zero workers (BR-001).
External Integration: None
Validation: Radius progression capped at 10km.
Test Requirement: Verify zero-result handling, radius progression advancement, navigation to Widen Search vs Post Job Fallback (5.1).

Backend API: GET /api/v1/jobs/{id}/manage, PATCH /api/v1/jobs/{id}

-------------------------------------------------------------------------------
Screen: 6.4 Select Hired Worker (kaamsetu.app/jobs/{id}/close/select)
-------------------------------------------------------------------------------
User Flow: Flow 06 — Employer Dashboard
Backend API: POST /api/v1/jobs/{id}/hire
Database Entity: jobs, hire_confirmations, job_interests
Business Rules:
- Selecting a worker calls `POST /jobs/{id}/hire`, which atomically: (1) validates that the selected worker expressed interest, (2) creates a `hire_confirmations` record (`employer_confirmed = true`, `worker_confirmed = NULL`, `status = PENDING`), (3) sets `jobs.status = CLOSED` and `jobs.close_reason = HIRED_VIA_KAAMSETU`, (4) generates HIRE_INITIATED audit entry, and (5) triggers worker notification flow (BR-004).
- There is NO secondary call to `PATCH /api/v1/jobs/{id}/close`.
External Integration: Firebase Cloud Messaging (prompts worker)
Validation: Selected worker must have expressed interest in the job.
Test Requirement: Verify atomic creation of `hire_confirmations` row with status PENDING, transition of job status to CLOSED with close_reason HIRED_VIA_KAAMSETU, sending confirmation prompt to worker.

9. FLOW 09: HIRE CONFIRMATION
===============================================================================

-------------------------------------------------------------------------------
Screen: 9.1 Two-Sided Hire Confirmation Prompt (kaamsetu.app/home)
-------------------------------------------------------------------------------
User Flow: Flow 09 — Two-Sided Hire Confirmation
Backend API: GET /api/v1/hire-confirmations/pending, POST /api/v1/hire-confirmations/{id}/respond
Database Entity: hire_confirmations, jobs
Business Rules:
- Employer selection creates `hire_confirmations` (`employer_confirmed = true`, `worker_confirmed = NULL`, `status = PENDING`) AND sets `jobs.status = CLOSED`.
- Worker responds YES (`confirmed = true`): `worker_confirmed = true`, `status = CONFIRMED`. Hire is fully confirmed (BR-004).
- Worker responds NO (`confirmed = false`): `worker_confirmed = false`, `status = MISMATCH`. The hire is NOT confirmed. The job remains `CLOSED` (does not automatically reopen). Auto-generates `HIRE_MISMATCH_FLAGGED` in `audit_logs` for admin review (BR-004).
External Integration: Firebase Cloud Messaging
Validation: Pending confirmation must exist.
Test Requirement: Verify worker confirming -> status CONFIRMED; worker denying -> status MISMATCH & audit log while job remains CLOSED.

-------------------------------------------------------------------------------
Screen: 9.2 Hire Confirmed Success Screen (kaamsetu.app/home)
-------------------------------------------------------------------------------
User Flow: Flow 09 — Two-Sided Hire Confirmation
Backend API: NOT DEFINED IN SOURCE (Client-side view)
Database Entity: worker_profiles
Business Rules: Confirmed hire increments "Recently completed hires" count calculated dynamically on Skill Passport.
External Integration: None
Validation: None
Test Requirement: Verify navigation to My Applications.
