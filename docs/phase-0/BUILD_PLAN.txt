EXECUTIVE SUMMARY & DEPENDENCY STRATEGY
-------------------------------------------------------------------------------
The implementation roadmap for KaamSetu is organized into 7 sequential phases covering 22 API capability groups across the complete REST endpoint surface (32 concrete endpoints).
The recommended phase order strictly obeys the dependency graph of the domain:

  Phase 1: Authentication, Onboarding & System States
  Phase 2: Employer Worker Search & Match Intelligence Engine
  Phase 3: Worker Home & Opportunity Discovery
  Phase 4: Employer Dashboard, Job Management & Fallback Job Posting
  Phase 5: Two-Sided Hire Confirmation & Worker Applications
  Phase 6: Admin Console & Incident / Report Management
  Phase 7: PWA, Offline Capabilities, Notifications, Security & Prod Readiness

DEPENDENCY RATIONALE:
1. Search & Match Intelligence (Phase 2) MUST precede Worker Home (Phase 3) because
   Worker Home renders "Best Match Today", "Closest Opportunity", and "Highest Salary"
   which rely directly on the Match Intelligence scoring algorithm and PostGIS query engine.
2. Employer Search (Phase 2) MUST precede Fallback Job Posting (Phase 4) because
   posting a job is strictly a fallback path triggered when search yields no results.
3. Two-sided Hire Confirmation (Phase 5) depends on active job interest lifecycle from
   Phases 3 & 4.
4. Admin & Reporting (Phase 6) depend on data emitted by all core user flows.
5. Production Readiness (Phase 7) hardens the validated end-to-end platform.

- 11.1  Forgot PIN (kaamsetu.app/forgot-pin)
- 11.2  Location Permission Prompt (kaamsetu.app/permissions)
- 11.3  Notification Permission Prompt UI (kaamsetu.app/permissions)
- 11.6  Session Timeout (kaamsetu.app/login)

FRONTEND WORK:
- Next.js responsive pages at mobile resolution (~375-414px).
- Low-literacy UI primitives: 44px+ touch targets, 6-digit PIN input UI component with box focus.
- Form validation hooks for mobile numbers, PIN matching, and mandatory address/experience fields.
- Permission prompt screens for Browser Geolocation and Notification UI states (Allow / Not Now / Denied).
- Auth state context / JWT storage in HttpOnly cookie / secure state.
- Optional shop photo placeholder UI on 3.2 rendered per wireframe. Permissions Required: None in Phase 1. Shop photo is a non-functional placeholder. Camera/file permission and S3 media upload are deferred to Phase 7. Photo upload is optional and does not block onboarding.
- Notification permission screen 11.3 UI handles Allow/Denied client states only. No Firebase Cloud Messaging SDK is integrated, no FCM token is registered, and `POST /api/v1/users/me/fcm-token` is NOT called in Phase 1 (deferred to Phase 7).
- Worker onboarding (Screen 1.4) displays "Set myself Available now" as an INITIAL PROFILE PREFERENCE (`is_available` boolean flag stored via worker profile update API). Phase 1 stores only the worker's initial `is_available` preference. `available_until` remains NULL until the Phase 3 availability engine initializes and manages it. Phase 1 does not invoke the availability API or perform availability expiry.

BACKEND WORK:
- Auth Controller & Spring Security JWT generation/validation filter.
- Password/PIN hashing via bcrypt / Argon2.
- Redis integration for login rate-limiting (max 5 attempts per 15 mins per phone).
- Worker onboarding REST endpoints (POST /auth/signup/worker, GET/PATCH /workers/me).
- Employer onboarding REST endpoints (POST /auth/signup/employer, GET/PATCH /employers/me).
- Forgot PIN endpoints (POST /auth/forgot-pin/request-otp, POST /auth/forgot-pin/reset).
- Google Maps Geocoding integration to convert text addresses to PostGIS geography Point.
- Mock/Stub Aadhaar verification service: UI collects Aadhaar; mock service returns `aadhaar_verified = TRUE` and a generated `aadhaar_ref_id` token. The raw 12-digit Aadhaar number may be transmitted only as part of the secure verification request required by the Aadhaar verification service. It MUST NEVER be persisted in the KaamSetu database, written to application logs, returned in any API response, stored in browser/local/session storage, included in audit metadata, or otherwise retained after verification processing. Real provider integration remains deferred (`PENDING INTEGRATION DECISION`).

DATABASE WORK:
- Create `users`, `user_devices`, `worker_profiles`, `worker_experience`, `employer_profiles` tables.
- `user_devices` table is created as part of the schema foundation in Phase 1; Phase 7 handles token registration and operational use. `user_devices` exists structurally but remains UNUSED for token registration during Phase 1.
- Create spatial GiST indexes on `worker_profiles.location` and `employer_profiles.location`.
- Create composite indexes on `worker_experience(trade, profession)`.

APIS REQUIRED:
- POST /api/v1/auth/signup/worker
- POST /api/v1/auth/signup/employer
- POST /api/v1/auth/login
- POST /api/v1/auth/forgot-pin/request-otp
- POST /api/v1/auth/forgot-pin/reset
- POST /api/v1/auth/logout
- GET/PATCH /api/v1/workers/me
- GET/PATCH /api/v1/employers/me

BUSINESS RULES ENFORCED:
- PIN, not OTP, is the everyday login mechanism. OTP is restricted strictly to Forgot PIN recovery.
- Worker verification is ID-only (Aadhaar reference stub) for MVP. Employer verification is phone-only. Raw Aadhaar numbers are never stored or logged.
- Total work experience, trade, profession, previous shop name, languages are captured in Skill Passport.
- Address geocoding converts address into PostGIS Point(lon, lat, 4326).
- Worker onboarding "Available Now" toggle sets initial profile preference only; it does not start the real-time availability engine.

INTEGRATIONS:
- Google Maps Geocoding API.
- Redis cache for PIN attempt counters.
- Mock/Stub Aadhaar Verification Service (marked `PENDING INTEGRATION DECISION`).

PHASE 2: EMPLOYER WORKER SEARCH & MATCH INTELLIGENCE ENGINE
===============================================================================
OBJECTIVE:
Build the primary employer discovery engine ("Search Nearby Skilled Workers"), the
Match Intelligence scoring calculator, search filters, radius widening progression, and worker Skill Passport inspection.

SCREENS INVOLVED:
- 4.1  Search & Filters (kaamsetu.app/search)
- 4.2  Skill Passport / Worker Detail (kaamsetu.app/worker/{id} - Employer inspection view & Worker self-profile view)
- 4.3  No Match / Zero-State (kaamsetu.app/search)

FRONTEND WORK:
- Filter UI components: Trade, Profession, Available Now toggle, Verified chip, Salary/Experience/Radius chips.
- Worker result card rendering with live Match Intelligence % badges and match factor breakdown tags.
- Skill Passport UI screen rendering core skills, experience by trade, previous employers, shop categories (derived from unique trade ENUMs), languages, completed hires count (derived dynamically from 3-month confirmed hires), and address.
- Dual perspective handling on 4.2:
  * Employer view: Displays "View Contact Number" and "Report this worker".
  * Worker self-view: Hides Contact Reveal & Report links; displays prominent "Edit Profile" button routing to 1.2/1.3/1.4.
- Contact Reveal button triggering API and displaying unmasked phone number.
- Zero-state view presenting "Widen Search" (advancing radius: 1km -> 3km -> 5km -> 10km max) and "Post a Job Need Instead" options.

BACKEND WORK:
- Implement PostGIS spatial query engine (`ST_DWithin`, `ST_Distance`).
- Implement Match Intelligence Scoring Engine:
  * Trade match (35%)
  * Profession match (30%)
  * Experience relevance (15%)
  * Distance scoring (15% within radius)
  * Availability scoring (5%)
- Search API endpoint (`GET /api/v1/search/workers`) with multi-criteria dynamic SQL/PostGIS filtering.
- Worker detail endpoint (`GET /api/v1/workers/{id}`) returning scored profile and derived shop categories & 3-month completed hires count.
- Contact reveal endpoint (`GET /api/v1/workers/{id}/contact`) with authorization check and audit logging.

DATABASE WORK:
- Optimize spatial GiST index on `worker_profiles.location`.
- Ensure composite index on `worker_profiles(is_available, available_until)`.
- Ensure index on `worker_experience(trade, profession, worker_id)`.

APIS REQUIRED:
- GET /api/v1/search/workers
- GET /api/v1/workers/{id}
- GET /api/v1/workers/{id}/contact

BUSINESS RULES ENFORCED:
- Search is the primary employer action everywhere (search-first architecture).
- Widen search advances radius along fixed progression: 1km -> 3km -> 5km -> 10km (capped at 10km for MVP).
- Workers outside search radius are completely excluded from results (not just down-weighted).
- Workers with expired availability (`available_until < NOW()`) are treated as unavailable.
- Contact number is shielded and revealed ONLY upon explicit GET /workers/{id}/contact API call.
- Audit log entry created whenever an employer reveals a worker's contact number.

INTEGRATIONS:
- PostGIS spatial functions for distance calculation in meters/kilometers.

VALIDATION & EDGE CASES:
- Zero workers found within radius triggers 4.3 zero-state UI with Widen Search CTA.
- Employer attempting to search without set business address (defaults to business trade & location).
- Unauthenticated access blocked on contact reveal.

TESTING REQUIREMENTS:
- Unit tests: Match Intelligence scoring logic across various edge case parameter combinations (confirming exact math e.g. 88.0%).
- Database tests: Spatial distance queries accuracy against known coordinates.
- Performance benchmark: GET /search/workers execution time under 1 second for 1,000 active profiles.

DEPENDENCIES:
- Phase 1 complete (user identity and profiles populated).

COMPLETION CRITERIA:
- Employers can filter nearby workers by trade, profession, availability, distance, and experience.
- Match Intelligence scores calculate dynamically with exact percentage breakdown.
- Widen search progressively expands search radius up to 10km cap.
- Contact reveal returns worker phone number and records audit log.

- Integration tests: Creating job -> editing job -> worker expressing interest -> employer invoking `POST /jobs/{id}/hire` -> verifying atomic `CLOSED` job status and `PENDING` hire confirmation record.

DEPENDENCIES:
- Phase 2 & Phase 3 complete.

COMPLETION CRITERIA:

PHASE 5: TWO-SIDED HIRE CONFIRMATION & WORKER APPLICATIONS
===============================================================================
OBJECTIVE:
Implement the two-sided hire confirmation protocol, automatic audit logging for hire
mismatches, worker application tracking, and dynamic Skill Passport trust metrics.

SCREENS INVOLVED:
- 9.1   Hire Confirmation Prompt (kaamsetu.app/home)
- 9.2   Hire Confirmed Banner (kaamsetu.app/home)
- 10.1  My Applications List (kaamsetu.app/applications)
- 11.4  First-Time Empty State — Applications (kaamsetu.app/applications)

FRONTEND WORK:
- Hire confirmation popup/modal rendering employer name, role, salary, and dual action buttons ("Yes, I joined" / "No, I didn't join").
- Confirmation success view explaining updated "Recently completed hires" count on Skill Passport.
- My Applications screen displaying applied jobs, status badges (Notified, Viewed, Interested, Hired, Filled), and match % badges.
- Empty state UI for workers with no application history (11.4).

BACKEND WORK:
- Create hire confirmation record (`hire_confirmations` table).
- Pending hire confirmations API (`GET /api/v1/hire-confirmations/pending`).
- Respond to hire confirmation API (`POST /api/v1/hire-confirmations/{id}/respond`):
  * Worker responds YES (`confirmed = true`): sets `worker_confirmed = true`, `status = CONFIRMED`. Hire is fully confirmed.
  * Worker responds NO (`confirmed = false`): sets `worker_confirmed = false`, `status = MISMATCH`. Job remains `CLOSED` (does not auto-reopen). Writes `HIRE_MISMATCH_FLAGGED` audit log.
- Worker applications list API (`GET /api/v1/workers/me/applications`).

DATABASE WORK:
- Create `hire_confirmations` table with FK constraints to `jobs` and `worker_profiles`.
- Unique constraint on `hire_confirmations(job_id, worker_id)`.

APIS REQUIRED:
- GET /api/v1/hire-confirmations/pending
- POST /api/v1/hire-confirmations/{id}/respond
- GET /api/v1/workers/me/applications

BUSINESS RULES ENFORCED:
- A hire is fully CONFIRMED only when both employer (`employer_confirmed = true`) and worker (`worker_confirmed = true`) respond YES.
- If worker responds NO (`worker_confirmed = false`), status becomes `MISMATCH`. The job remains `CLOSED` (no automatic reopening). The employer must post a new job if they wish to search again.
- Confirmed hires in the last 3 months dynamically calculate the "Recently completed hires" count on the worker's Skill Passport.
- A mismatch auto-generates an `audit_logs` record for admin review (`HIRE_MISMATCH_FLAGGED`).

INTEGRATIONS:
- Internal event dispatcher for hire confirmation status changes.

VALIDATION & EDGE CASES:
- Worker attempting to respond twice to the same confirmation prompt.
- Expired confirmation prompts (older than 7 days auto-flagged for review).
- Application list pagination and sorting by applied date.

TESTING REQUIREMENTS:
- Unit tests: Two-sided state machine (`PENDING` -> `CONFIRMED` vs `PENDING` -> `MISMATCH`, maintaining `CLOSED` job status).
- Integration tests: Worker confirming hire updates `hire_confirmations` and increments completed hires dynamic query result.

DEPENDENCIES:
- Phase 4 complete (employer hire selection functional).

COMPLETION CRITERIA:
- Worker receives hire confirmation prompt when selected by employer.
- Responding "Yes" marks hire CONFIRMED and updates Skill Passport.
- Responding "No" flags MISMATCH in audit log for admin review while keeping job CLOSED.
